# State Representation Options for a Personal World Model

**Scope.** This research compares storage and retrieval architectures for a Personal World Model (PWM) that must retain authoritative, versioned assertions; synchronize external sources; keep compact lineage; selectively disclose data; and serve bounded Context Bundles to open tasks. It is an architecture assessment, not a product decision or implementation plan. Sources were checked on 2026-09-09 and are primarily vendor documentation, source repositories, and W3C specifications.

## Evaluation Lens

The central distinction is between an **authoritative assertion ledger** and **derived retrieval projections**. An assertion should have a stable identifier, immutable content or revision, source locator and capture metadata, validity/transaction time, confidence or status, and a disclosure policy. A Context Bundle is a bounded, task-scoped projection containing assertion identifiers, selected revisions, provenance, and any generated material. Embeddings, graph edges inferred from text, summaries, and retrieval rankings are useful projections, but do not by themselves establish authority or lineage.

| Criterion | What good looks like for PWM |
| --- | --- |
| Atomic semantic commits | A single transaction can append assertions, supersession links, source-sync checkpoint, and disclosure metadata together; failed work leaves no partial state. |
| Versioning and compact lineage | Append revisions rather than mutate history; keep direct `supersedes`/`derived_from` references, content hashes, and source cursors. Materialize current state rather than duplicating full snapshots. |
| Query and retrieval | Exact identity, time, policy, and provenance filters precede lexical/vector ranking. Context assembly returns stable assertion IDs and citations. |
| Open-world data | New predicates, entities, source fields, and conflicting claims can arrive without destructive migrations. Unknown is distinct from false. |
| Selective disclosure | Authorization/policy is evaluated before a candidate can enter a bundle, including its derived chunks and embeddings. |
| Portability and operations | Canonical records have documented, exportable forms; projections can be rebuilt; self-hosting does not require an unnecessary distributed system. |

| **PostgreSQL relational core + JSONB + full-text + pgvector** | Strongest fit. PostgreSQL serializable transactions make a commit behave as a serial execution or fail for retry [1]. Primary/unique/foreign-key constraints can enforce assertion identity and direct lineage [2]. Version history is an application schema, not an automatic temporal model. | Relational columns handle identity, time, source, policy, and links; `jsonb` admits source-specific fields and supports GIN/jsonpath indexing [3]. Built-in full-text search plus pgvector supports hybrid retrieval in one database [4][5]. | Row-level security/policy design and transactionally maintained projection tables are feasible in one authority. SQL/JSON and ordinary export formats are portable; pgvector is an extension, so export canonical embeddings/metadata separately. | One operational system. `pgvector` exact search is the default; HNSW/IVFFlat are production features but approximate and trade recall for speed [5]. Best MVP baseline when correctness and auditability dominate. |
| **Dedicated vector database (Qdrant as representative)** | Durable point updates use a WAL, and APIs are idempotent, but the normal model is upsert/overwrite [6]. It does not provide a multi-entity relational semantic-commit boundary or lineage semantics. | Purpose-built vector retrieval with payload filters, dense/sparse/named vectors, and hybrid search. A point is a vector plus optional payload [6][7], not an assertion model. | Payload filters can carry a policy label, but policy and source-of-truth synchronization must be built and kept correct outside the vector store. Qdrant is self-hostable; the projection must be rebuildable from canonical state. | Adds synchronization, monitoring, replay, and authorization-drift failure modes. Appropriate later if corpus/latency exceeds in-Postgres needs; poor choice as sole authority. |
| **Property-graph database / knowledge graph (Neo4j representative)** | Neo4j operations run in ACID transactions [8], so a graph mutation can be atomic. Its graph model does not itself prescribe assertion revision, validity, or provenance; these remain a domain schema. | Cypher is expressive for relationship pattern matching and Neo4j is schema-flexible [9]. This is useful when multi-hop traversal is a first-order workload, not merely an occasional retrieval enhancement. | Self-hosting is supported, including Docker [10]. Property graph exports and Cypher are less interchange-standard than RDF; disclosure still needs policy-aware query/projection discipline. | A second data model, data pipeline, backup surface, and query skill set. This is the strongest standards-based interchange story. | RDF has standardized serializations including N-Triples, Turtle, TriG, and JSON-LD [11]. RDF 1.2 and SPARQL 1.2 are currently Candidate Recommendation/Working Draft; RDF 1.1/SPARQL 1.1 are the Recommendations [11][12]. Policy and temporal behavior are not standardized by RDF alone. | Requires a triple-store selection and ontology/query expertise. Strong interoperability option where external linked-data exchange or formal semantics are requirements; otherwise higher MVP modeling cost. |

Whole-document replacement can obscure compact per-assertion history. | Excellent for raw source snapshots and heterogeneous ingestion. Retrieval is generally document/chunk-oriented, so exact claim-level conflict, validity, and provenance queries need explicit modeled fields or a separate ledger. | JSON portability is high, but selective disclosure becomes difficult if a document mixes classifications. | Useful as a raw-source adjunct or a simpler product whose authority is documents; weaker as the sole assertion authority. |
| **Event store / append-only log** | Natural fit for immutable events and replay; semantic commit boundaries and expected-version concurrency are usually stream-oriented. It excels at change history but needs projections for current assertions and search. | Event streams preserve source-sync history well. Querying an arbitrary current world model, full text, vector search, and task bundle assembly are projection workloads, not the log's native access pattern. | Retention/erasure and policy changes require deliberate design because history is retained. Events can be portable, but schema evolution and projection rebuild operations are central. | Good if the product's primary invariant is event sourcing; otherwise it adds projection infrastructure earlier than needed. Prefer an append-only assertion table before adopting a separate event-store service. |
| **Graph-RAG pipeline** | Not an authority store. Microsoft describes GraphRAG as a pipeline that extracts a graph, communities, and summaries from raw text [13]. The project states that it is research, maintenance-mode, and not an officially supported offering [14]. | Can improve corpus-level and multi-hop question answering; its own docs retain a basic vector-search mode [13]. Extracted entities/relationships/claims are model-derived and must be evidence-linked, reviewable, and rebuildable. | It should never be the enforcement point for disclosure; retrieval inputs must already be policy-filtered. Its outputs are derived artifacts, not a portable canonical representation. | Experimental/research-only for this decision. Costly indexing and prompt tuning are documented [13][14]. Defer from MVP. |
| **Hybrid: authoritative relational ledger plus derived projections** | The ledger gives one commit boundary; an outbox/job cursor creates embeddings, chunks, graph edges, and search projections after commit. A projection can be deleted and rebuilt, while assertion IDs and lineage remain stable. | Combines deterministic filtered retrieval with lexical/vector ranking; introduce graph traversal or graph-RAG only for proven query classes. Use stable IDs, revision IDs, and source hashes so every projection result can resolve back to evidence. | Lowest irreversible complexity. Start with one PostgreSQL deployment; add a dedicated vector or graph service only against measured scale/retrieval requirements. |

## Production-Support Boundaries

* PostgreSQL JSONB, constraints, transactions, and full-text search are built-in documented database features [1][2][3][4]. `pgvector` is a separately installed open-source extension supporting PostgreSQL 13+; its exact search is default and its HNSW/IVFFlat indexes are approximate by design [5]. Treat it as a supported dependency with conventional extension upgrade/backup testing, not as core PostgreSQL.
* Qdrant documents durable WAL-backed point operations, payloads, and dense/sparse/named vectors [6][7]. This establishes vector-service capability, not ledger-grade multi-table semantic transaction support.
* Neo4j documents ACID transactions and production installation paths [8][10]. Its graph schema is flexible, so model constraints and version/lineage semantics remain application responsibilities [9].
* RDF 1.1 and SPARQL 1.1 are stable W3C Recommendations. The cited RDF 1.2 and SPARQL 1.2 documents are respectively Candidate Recommendation Snapshot and Working Draft, so triple-term/reification interoperability should be validated against a selected store before relying on it [11][12].
* Microsoft GraphRAG explicitly says it is a research project, is largely maintenance-mode, and is not an officially supported Microsoft offering [14]. It is not an MVP dependency for authoritative state or disclosure.

## Implications for the PWM Requirements

### Atomic semantic commits and source synchronization

The authoritative write should append the assertion revision, attach provenance, record source checkpoint/cursor, add direct lineage links, and update the current assertion view in one transaction. PostgreSQL's serializable isolation gives the needed all-or-nothing concurrency semantics, with required retry handling for serialization failures [1]. A separate vector/graph projection must not participate in that commit; instead, it consumes committed revision IDs idempotently and records its own projection version. This prevents an index outage from making authoritative source synchronization unavailable.

### Versioning and compact lineage

Do not use database MVCC row versions as product lineage: MVCC is concurrency machinery, not a durable domain-history API. Model append-only assertion revisions with stable assertion and revision IDs, direct `supersedes`, `derived_from`, `source_snapshot`, and optional `retracts` links. Store a content hash for deduplication/integrity and materialize the current revision. This retains one link per relationship rather than copying ancestral metadata into every revision. Relational foreign keys enforce only references to extant records [2]; semantic rules such as acyclic supersession and source cursor monotonicity need transaction logic/constraints designed for those invariants.

### Selective disclosure and Context Bundles

Disclosure cannot be recovered by post-processing a broad LLM context. Filter candidate assertion revisions by audience/purpose/policy and time before lexical/vector/graph retrieval, then construct a bounded bundle with evidence IDs, source locators, revision IDs, and policy-safe excerpts. Derived embeddings, chunks, summaries, and graph edges inherit or reference the governing policy. Treat each Context Bundle as an auditable read artifact: record task, retrieval policy/version, selected assertion revisions, and any generated summary provenance.

### Open-world data and interoperability

Use typed relational fields for invariants and `jsonb` for source-specific, evolving facts; PostgreSQL advises predictable document structure even when using JSONB [3]. Preserve original source payloads separately from normalized assertions. If standards-based interoperation later becomes a requirement, map assertion/revision/provenance records to RDF named graphs or an RDF dataset. RDF explicitly supports multiple named graphs/snapshots and standardized serializations, while recognizing that change over time is an added vocabulary concern [11].

## Evidence-Based MVP Position

For the stated requirements, the most conservative MVP architecture is a **PostgreSQL authoritative assertion ledger with JSONB source payloads, built-in full-text search, and pgvector only as a derived in-database retrieval index**. This is an assessment, not a product decision. Its decisive advantage is one transactional authority that can enforce assertion identity, revision links, source synchronization checkpoints, and disclosure metadata, while retaining flexible source fields and supporting hybrid retrieval without cross-service consistency.

Key tradeoffs:

* This does not make vector retrieval exact when using HNSW/IVFFlat; the authoritative filters must run first, and recall must be evaluated against exact search [5].
* It does not provide native graph traversal ergonomics or semantic-web interchange. Add a graph projection/database only when measured Context Bundle requests depend heavily on multi-hop traversal.
* An append-only ledger and projections require deliberate retention, reindexing, and migration procedures, but those are simpler than synchronizing two authoritative stores.
* Dedicated vector DBs, graph DBs, RDF stores, document stores, and event stores each solve real specialized problems. None substitutes for an explicit authority/provenance/disclosure model.
